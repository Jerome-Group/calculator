# Verification boundaries

The source inventory, mathematical oracle, rendered application and disconnected runtime establish different facts. A correct engine answer cannot establish that a form represents its inputs correctly, its controls work, or the browser can reopen without its origin.

Start with `pnpm --silent verify --help`, `list --json`, then `show <ID> --json`. The versioned contract is [verification-map.json](verification-map.json). Independent default and choice fixtures live in `tests/fixtures/`; command contracts and evidence checks live in `scripts/verification-*.mjs`. `pnpm --silent verify doctor --suite math --json` reports prerequisites without preparing assets. `doctor --group core --json` checks every selected suite and blocks if any prerequisite is unavailable; plain `doctor` checks only Node. `show core --json` lists the group’s suites.

`show editor.menu --json` follows the fixtures’ grouping tag to their IDs and owning feature IDs; vendor-menu groups remain separate from the catalogue’s operation surfaces.

`pnpm --silent verify run --group core --json` provides one local/CI entrypoint. It runs the owned checks and build closure; its result explicitly records browser verification as `not-run`. The map declares preparation's possible network use and writes separately from no-fetch mathematical execution. Default fixtures and choice fixtures are independent mathematical expectations, not captured implementation snapshots. Approximate values use finite tolerances; bases and solution families also check dimensions or independent parameters, avoiding sign-sensitive snapshots and incomplete residual-only checks.

`pnpm --silent verify run --group deep-math --json` runs valid/invalid mathematical contracts, the observed-result adapter and failure detectors. `--group regressions` isolates editor, notation, display, graph, worker, result-validation and async-component regressions. These regressions also run once through canonical `pnpm test`, which `core` invokes.

`pnpm --silent verify run --suite math --fixture form.matrix_inverse.default --json` runs one fixture. Omitting `--fixture` runs all mathematics fixtures. The runner records standard output/error and structured results in a temporary evidence directory; `--evidence-dir` chooses a directory. Nothing here writes an account workspace or publishes a deployment.

`pnpm --silent verify prove-detectors --case math.scalar --json` proves a real result assertion fails after replacing the returned matrix, then passes again. `catalogue.mapping` removes an actual form mapping in a disposable source fixture. `evidence.stale` proves the evidence reader rejects a stale revision and wrong artifact hashes. These cases do not establish browser/offline/security mutation coverage. An intentionally thrown exception is a harness check, not a mathematical failure detector.

Browser evidence is separately checked by `pnpm --silent verify browser validate --evidence <manifest.json> --json`. A successful record requires the current Git revision, a digest including dirty tracked/untracked source files, the built offline-manifest digest, the required browser fixture IDs, recorded steps/assertions, and artifact hashes. Missing records, unfinished checks and previous-revision observations cannot certify current readiness. Evidence validation reads recorded observations; it does not operate a browser. Browser files can contain synthetic local observations, so keep evidence outside the public source tree.

Exit codes: `0` pass; `1` assertion/evidence failure; `2` invalid arguments or schema; `3` unavailable prerequisite; `4` harness failure. `pnpm --silent verify … --json` or `node scripts/verify.mjs … --json` produces one JSON envelope on standard output; plain pnpm adds an ELIFECYCLE line on nonzero exits, so automated readers must use either supported form; child logs are artifacts. Suite metadata names the actual log/result files; suites without a structured child report record process-level checks in `manifest.json`, while coverage records its checks directly in that manifest. No `core` success substitutes for the browser, invalid/boundary inputs, account races, mobile interaction, multiple themes or genuine disconnected reopening.

If a launcher reports the pinned pnpm version but nested checks see another version, set `CALCULATOR_PNPM` to the absolute pinned pnpm executable or its `.cjs`/`.mjs` entrypoint, then run `node scripts/verify.mjs doctor --group core --json` (and subsequent commands) with that environment. The override changes only this invocation; it does not install pnpm or change global settings. Confirm the doctor reports `11.25.0` before running suites. Node 24 must also be on PATH.
